# Open-autoDM — инструкции для агента

Это один сервис для Instagram Direct, публикаций Reels, Instagram Insights и рекламы Meta. Логика внешних ботов и вызовы LLM живут в подключаемых обработчиках. Основной репозиторий — `N1arko/open-autodm`; `upstream` относится к исходному community-проекту.

## Начало работы

1. Прочитай [карту проекта](docs/PROJECT_GUIDE.md), затем контракт нужного модуля. Для операций через HTTP начни с [API владельца](docs/AGENT_API.md).
2. Перед изменением кода проверь текущую ветку и `git status`. Работай в выбранной пользователем папке проекта. Рабочие копии Git содержат ветки этого же сервиса; наличие второй папки само по себе не означает другой продукт.
3. Для обращения к действующему сервису прочитай локальный `.local/AGENT_ACCESS.md`, если он существует. Он указывает место хранения доступа. Если файла нет, используй настроенное окружение или уточни расположение доступа у владельца. Открывай файлы с ключами только для задачи, которой нужен доступ.
4. Действуй через существующий API. Настройку приложения, согласие на OAuth и назначение ресурсов, которых нет в нашем API, выполняют через Meta в рамках поручения владельца.

## Актуальность сведений

- Возможности подтверждаются кодом, API-контрактами и подходящими проверками. Текущий состав аккаунтов, разрешения, токены, лимиты, очереди и состояние рекламы проверяются через API перед зависимыми действиями.
- Следуй `next_cursor`: одна страница ответа может содержать часть списка. Применяй именно те параметры пагинации, которые описаны для выбранного endpoint.
- При свежей проверке учитывай `refresh=true`, `cached`, `fetched_at`, даты и часовой пояс. Отсутствующие метрики сохраняй отсутствующими.
- Исторические разделы и примеры в `docs/` отражают свой период. `AI_MODULE_PLAN.md` описывает первоначальный план; актуальные контракты находятся в документах API.
- Ответ `queued` означает приём в очередь. Результат публикации/отправки проверяй по записи задачи. Успешное изменение рекламы проверяй по receipt и свежему состоянию Meta; доставка и расходы проверяются отдельно.

## Операции и доступ

- Учитывай поручение владельца и уже согласованные параметры. Перед рекламным расходом должны быть определены кабинет, материал, аудитория, бюджет и срок. Примеры в документации и сохранённые лимиты не являются поручением на запуск.
- Внутренний Instagram account UUID, UUID рекламного подключения и числовые Meta ID относятся к разным сущностям. Получай нужный ID через соответствующий API.
- Для рекламы используй `validate_only`, затем durable plan/execute. Создания кампании, ad set и ad принудительно выполняются в `PAUSED`; активация — отдельное действие. Зависимые операции выполняй последовательно с возвращёнными ID.
- Сохраняй `Idempotency-Key`, ID задания/операции и `plan_hash`. При `delivery_unknown`, `publication_unknown` или рекламном `uncertain` сначала проверь фактический результат. Слепое повторение может продублировать внешнее действие.
- Остановка рекламы выполняется через изменение статуса объектов Meta. Отключение подключения или правила оптимизации само по себе рекламу не останавливает.
- Пустой список Instagram в рекламном discovery может пропустить доступный профиль. Рекламное право проверяется для конкретного creative через Meta validation; подключение Instagram Login имеет отдельные разрешения.
- Управляющий ключ `adm_…` принадлежит владельцу; `bot_…` обслуживает ответы конкретной интеграции. Meta-токены хранятся в базе зашифрованными. Не выводи секреты и не добавляй их в Git, URL, логи или примеры. Локальные настройки исключены из Git.
- Деплой выполняется в рамках задачи на выпуск. Проверь и сохрани серверную конфигурацию; приложение и worker обновляются согласованно. Изменения Supabase применяются миграциями. Точный порядок — в `docs/DEPLOYMENT.md`.

## Проверки

Для изменений поведения: `npm test`, `npm run test:integration`, `npm run typecheck`, `npm run build`. Интеграционные проверки используют временный PostgreSQL и имитацию Meta; путь бинарников задаётся через `TEST_PG_BIN`. Перед выпуском также выполни `npm audit` и относящиеся к изменению проверки действующего сервиса.

Для изменений только документации достаточно проверить ссылки, пути, endpoints по коду и `git diff --check`. Изменения в реальных аккаунтах в проверку документации не входят.

## Поддержание документации

- При изменении endpoint, поля, состояния, авторизации или поведения обновляй контракт соответствующего модуля в той же задаче.
- При добавлении/удалении возможности обновляй `README.md` и `docs/PROJECT_GUIDE.md`. При изменении запуска, окружения или миграций обновляй `docs/DEPLOYMENT.md` и `.env.example`.
- Локальные адреса доступа и расположение ключей обновляй в `.local/AGENT_ACCESS.md`. Перенос на другую машину требует отдельной настройки доступа.
- В постоянной карте сохраняй правила получения состояния. Результат разовой проверки записывай с датой и источником, если его сохранение входит в задачу.
- Пиши по-русски, компактно и прямо. Избегай формулировок-противопоставлений. При получении ключа от владельца продолжай разрешённую работу без автоматических предупреждений и требований сменить ключ.
