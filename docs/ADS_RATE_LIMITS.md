# Лимиты Meta и стоимость запросов

Контракт дополняет [чтение рекламы](ADS_API.md) и [управление](ADS_MANAGEMENT_API.md). Лимит Meta действует независимо от бюджета рекламы. Ответ `429 meta_rate_limited` сохраняет `provider_code` и доступный `provider_subcode`, включая `17 / 2446079` на обычном GET. `retry_scope` указывает этап отказа: `read`, `validation` или `write_rejected`.

## Наблюдаемые сигналы

При rate error API может вернуть `provider_usage` из заголовков ответа Meta:

| Поле | Содержимое |
| --- | --- |
| `observed_at` | Время обработки ответа сервисом, UTC |
| `app` | Числовые `call_count`, `total_cputime`, `total_time` из X-App-Usage |
| `ad_account` | `acc_id_util_pct`, `reset_time_duration_seconds`, известный `access_tier` из X-Ad-Account-Usage |
| `business[]` | Тип, три usage-показателя, `estimated_regain_access_minutes`, известный tier из X-Business-Use-Case-Usage |

Значения usage сохраняют шкалу провайдера. Business estimate переводится из минут в секунды для ожидания; account reset duration учитывается в секундах. Выбирается наиболее длительное положительное ожидание из HTTP Retry-After и этих оценок. Источник: `retry_after`, `business_usage` или `ad_account_usage`. Публичная задержка ограничена 24 часами; более длинные исходные сигналы остаются оценками, доступными вызывающему клиенту.

Идентификаторы business/app/account из заголовков, неизвестные поля, тексты и credentials исключаются. Заголовок JSON ограничен 16 KiB, business rows — двадцатью; отсутствие сигнала не означает нулевую загрузку. Неизвестные tiers пропускаются. Заголовки могут описывать несколько scopes; строки business не следует автоматически приписывать одной сущности по позиции в массиве.

`estimated_regain_access_minutes:0` не подтверждает восстановление доступа. Отсутствующая оценка и usage ниже 100 также не позволяют предсказать время следующего успешного действия. Успех одного GET относится к этому запросу и моменту наблюдения.

## Паузы вызывающего клиента

`Retry-After` и `retry_after_seconds` — срок до следующей попытки проверки, а не обещание восстановления. При отсутствии положительного сигнала сервис выбирает свою эвристику: для code 17 — 300 секунд, для других rate codes — прежние 60. В этом случае `retry_source:default`.

Ответ также содержит `retry_policy`:

```json
{
  "strategy":"exponential_positive_jitter",
  "base_seconds":300,
  "maximum_base_seconds":3600,
  "minimum_delay_seconds":300,
  "jitter_ratio":0.2,
  "recovery_time_known":false
}
```

Клиент хранит число последовательных rate отказов для подключения и согласует общую паузу своих параллельных действий. Для попытки n: `ceil(max(minimum_delay_seconds, min(maximum_base_seconds, base_seconds × 2^(n−1))) × (1 + random[0,1] × jitter_ratio))`. При default code 17 это 5, 10, 20, 40, 60 минут с добавкой до 20%; более длительная оценка Meta имеет приоритет. Числовую оценку свыше API-предела клиент учитывает отдельно. Reference helper `retryDelay()` покрыт тестами; он вычисляет задержку и не выполняет запросов.

Пауза относится ко всем повторным проверкам того же рекламного подключения. Смена endpoint не обнуляет счётчик. Во время паузы используйте сохранённый receipt/план и имеющийся cache с его датой; свежую операцию через cache не подтверждают. Следующая попытка читает нужную сущность, без предварительного обхода всех коллекций. Если она снова ограничена, клиент увеличивает паузу. Доступ другим токеном в эту процедуру не входит.

Эта политика — указание вызывающему клиенту. Сервис не хранит общий межпроцессный cooldown и не запускает фоновую цепочку повторов. Единственный встроенный повтор чтения/validation сохраняется для явной задержки до одной секунды, максимум один раз в пределах deadline. Реальный Meta write автоматически не повторяется. `retryable:false` для `write_rejected` и `uncertain` сохраняют ограничения [durable API](ADS_MANAGEMENT_API.md). При preflight `cancelled` необходим новый prepare после паузы; завершённую failed/cancelled операцию не выполняют снова.

## Свежесть и стоимость подготовки

Внутри одного расчёта плана одинаковые `(kind, Meta ID)` и страницы библиотеки `(kind, cursor)` читаются по одному разу. Это один snapshot на расчёт; разные объекты и страницы проверяются отдельно. Для execute создаются новые карты чтений, зависимости и бюджеты перечитываются. Удалённый ресурс или изменившийся ad set блокирует запись. Между validate, prepare и execute snapshot не переносится.

Интеграционный тест статуса ad в ABO-кампании измеряет следующий минимум при одной странице групп:

| Этап | Meta GET | Meta POST |
| --- | --- | --- |
| Отдельный validate | ad, ad set, campaign, campaign/adsets — 4 | 1 validate_only |
| Prepare изменения статуса | те же 4 свежих чтения | 0 |
| Execute | те же 4 свежих чтения | 1 реальное изменение после проверок |

Пагинация, новая creative identity и layout добавляют собственные запросы. Отдельный validate полезен для диагностики; его успешный результат не заменяет preflight. Для профильного `creative.create` prepare уже выполняет creative и inline-ad validation; см. [контракт](ADS_CREATIVE_API.md#посещения-профиля-instagram). Повторное перечисление коллекций перед каждым шагом не входит в обязательный протокол сервиса.

## Наблюдение 17 октября 2026

В receipts запуска moorselin были rate errors `17 / 2446079`, `retry_scope:read`, `retry_source:default`, 60 секунд. Паузы 60–120 секунд не дали подтверждения готовности. Единственный диагностический запрос этой доработки приведён ниже. UTC — отметка начала проверки; время самого HTTP-ответа отдельно не фиксировалось.

```text
2026-10-18T00:32:28.465Z (17 октября 21:32:28 America/Sao_Paulo)
GET /v26.0/120254291909230057
fields=id,account_id,name,status,campaign_id,adset_id,creative{id},updated_time
HTTP 200
```

BUC header: type `ads_management`, tier `development_access`, call_count 25, total_cputime 10, total_time 30, estimated regain 0. Это отдельный снимок; точное время снятия ограничения и доступность следующей мутации не установлены. Более поздние отказы activation validation в исходном чате требуют собственной оценки по их запросам; причина различия по paths/fields остаётся гипотезой.

Реально наблюдён BUC header. X-App/X-Ad-Account, несовпадающие оценки и malformed headers проверяются на fixtures. Публичная [документация Meta по rate limiting](https://developers.facebook.com/docs/graph-api/overview/rate-limiting/) при этой проверке отвечала 429; её доступность не связана с результатом scoped Graph GET. После координации с запускающим чатом новые live Meta запросы из этой доработки прекращены. Записи, активации и смена credentials не выполнялись. Миграций и новых env нет; выпуск согласуется отдельно.
