# API внешних ботов

Сервис доставляет сообщения между Instagram и внешними обработчиками. Логика, история диалога для ИИ и вызовы OpenRouter принадлежат внешнему боту. Существующий интерфейс open-autoDM используется для подключения Instagram и настройки Meta.

Один аккаунт привязывается к одной интеграции. Интеграция может обслуживать несколько аккаунтов. Число интеграций определяется данными в базе; ограничений на 5 или 100 в коде нет.

## Регистрация и привязка

Управляющие запросы используют `Authorization: Bearer <Supabase user access_token>` либо постоянный ключ владельца `adm_…`, если он настроен на сервере. Порядок управления без панели описан в [AGENT_API.md](AGENT_API.md). Ответы API имеют `Cache-Control: no-store`.

```http
POST /api/v1/integrations
Content-Type: application/json
Authorization: Bearer <owner JWT>

{"name":"Milly backend","webhook_url":"https://bot.example.com/events"}
```

Ответ 201 содержит `id`, `token` и `webhook_secret`. Эти два секрета возвращаются один раз. В базе сохраняются хеш токена и зашифрованный секрет подписи.

```http
PUT /api/v1/accounts/<account UUID>/integration
Content-Type: application/json
Authorization: Bearer <owner JWT>

{"integration_id":"<integration UUID>"}
```

`account UUID` — внутренний `id` из существующего `GET /api/instagram/accounts`. Удаление привязки: `DELETE` по тому же адресу. Каждая смена привязки увеличивает её ревизию. События и ответы предыдущей ревизии больше не отправляются. Запрос к Instagram, уже начавшийся в момент переключения, может завершиться.

Управление:

| Метод и путь                                 | Назначение                                             |
| -------------------------------------------- | ------------------------------------------------------ |
| `GET /api/v1/integrations?cursor=<UUID>`     | Список владельца, до 50 строк и `next_cursor`          |
| `GET /api/v1/accounts/<id>/integration`     | Текущая привязка аккаунта и её ревизия                 |
| `PATCH /api/v1/integrations/<id>`            | `name`, `webhook_url`, `enabled`                       |
| `POST /api/v1/integrations/<id>/credentials` | Выпустить новую пару секретов, аннулировать предыдущую |
| `PATCH /api/v1/conversations/<id>`           | `{"paused":true}` или `{"paused":false}`               |

Пауза диалога или выключенная интеграция задерживает ожидающие задания. Повторная проверка происходит через 60 секунд. Открытое окно переписки проверяется снова непосредственно перед отправкой.

## Входящее сообщение боту

Сервис отправляет `POST` на `webhook_url`:

```json
{
  "version": "1",
  "event_id": "<UUID>",
  "type": "message.received",
  "integration_id": "<UUID>",
  "account_id": "<UUID>",
  "conversation_id": "<UUID>",
  "message": {
    "id": "<same event UUID>",
    "external_id": "<Meta mid>",
    "text": "Hello"
  },
  "sender": { "external_id": "<Instagram scoped sender ID>" },
  "occurred_at": "2026-10-03T20:00:00+00:00"
}
```

Заголовки: `X-Bot-Event-Id`, `X-Bot-Timestamp` (Unix seconds) и `X-Bot-Signature`. Подпись: `sha256=` + hex HMAC-SHA256 от `<timestamp>.<raw HTTP body>` с ключом `webhook_secret`. Проверяйте подпись по исходным байтам, временное окно ±5 минут и уникальность `event_id`.

Любой HTTP 2xx подтверждает приём. Повторная доставка использует тот же event ID и тело, новую метку времени и подпись. Доставка имеет семантику at-least-once: обработчик должен дедуплицировать события. Максимум 10 попыток с задержкой 5 секунд, затем удвоение до часа. После исчерпания задание остаётся в `bot_transport_jobs` со статусом `failed`; повторный запуск требует вмешательства оператора. Боту с долгой генерацией следует сохранять событие и быстро отвечать 202, затем вызвать API ответа отдельно.

Для аккаунта с привязкой текстовые DM и текстовые ответы на Stories передаются интеграции. Кнопки `SESSION_*` продолжают существующий сценарий. Без привязки работают прежние keyword automation. Комментарии продолжают существующую обработку. Echo/read/delivery и сообщения самого аккаунта отфильтровываются. Вложения без текста в этой версии не передаются боту.

## Ответ бота

```http
POST /api/v1/messages
Authorization: Bearer <integration token>
Idempotency-Key: answer:<event UUID>:1
Content-Type: application/json

{"conversation_id":"<UUID>","in_reply_to_event_id":"<event UUID>","text":"Hey!"}
```

Ответ 202: `message_id`, `conversation_id`, `status`, `external_id`, `error_code`. Длина текста 1–1000 символов; тело запроса до 8 KiB. `in_reply_to_event_id` обязателен и должен принадлежать текущей привязке и диалогу. Адресат и Instagram-аккаунт определяются сервером. Токен интеграции даёт доступ только к её сообщениям и привязанным диалогам.

Одинаковый `Idempotency-Key` и тело возвращают прежнее сообщение; другой текст/диалог/event с тем же ключом возвращает 409. Ключ 1–128 символов: буквы, цифры, `_ . : -`. Уникальность действует в пределах интеграции. Сохраняйте ключ между повторами запроса.

`GET /api/v1/messages/<message_id>` с тем же токеном возвращает состояние:

- `queued` — ожидает отправки;
- `sending` — начался запрос к Instagram;
- `sent` — Meta вернула ID сообщения;
- `failed` — подтверждённый отказ или закрывшееся окно/смена привязки;
- `delivery_unknown` — запрос мог пройти, но подтверждения нет. Автоматического повтора нет. Оператор проверяет переписку прежде, чем принимать решение о новом сообщении.

403 используется для неверной Meta-подписи; API ботов использует 401 для неверного токена, 404 для чужого/отсутствующего ресурса, 409 для конфликта, паузы или закрытого окна, 413/415 для размера/формата, 503 для временной недоступности базы.

## Пример и запуск

`npm run bot:example` запускает внешний echo-бэкенд на `127.0.0.1:8788/events`. Переменные: `TRANSPORT_API_URL`, `BOT_TOKEN`, `BOT_WEBHOOK_SECRET`, необязательная `BOT_PORT`. Меняйте генерацию ответа в `scripts/echo-bot.ts` на вызов своего агента. Ключ OpenRouter передаётся только этому внешнему агенту.

HTTPS endpoints должны разрешаться в публичные IP. DNS проверяется при регистрации и при каждой доставке; проверенный адрес закрепляется за соединением. Перенаправления не выполняются. Внутренние endpoints разрешаются только через явный список `BOT_WEBHOOK_ALLOWED_HOSTS`; он также позволяет HTTP для доверенных внутренних имён. Например, добавление `127.0.0.1` подходит для локального примера, а в Docker указывайте DNS-имя контейнера бота.

Запросы к боту и Meta ограничены 10 секундами. Очередь обрабатывается независимо от прежних automation. Задания одного направления в одном диалоге выполняются последовательно. Выборка даёт интеграциям очередь по времени последнего запуска; занятый бот не занимает все места в одном пакете. Несколько worker-процессов используют атомарные claims и токены аренды.

Raw Meta webhooks сохраняются до подтверждения 200 и очищаются через 7 дней после завершения маршрутизации. Транспортные сообщения, ключи идемпотентности и завершённые задания сохраняются 30 дней. История для ИИ должна жить у внешнего бота. Резервные копии базы и наблюдение за `failed`/`delivery_unknown` задаются оператором отдельно.

Проверки: `npm test`, `npm run test:integration`, `npm run typecheck`, `npm run build`. Интеграционные тесты запускают отдельный временный PostgreSQL и применяют все миграции. Нужны PostgreSQL binaries; задайте `TEST_PG_BIN`, если они установлены не в `/opt/homebrew/opt/postgresql@16/bin`. Тесты используют подменённую Supabase auth/REST HTTP-оболочку с реальной SQL-базой и имитацию Meta; живые аккаунты не затрагиваются.
