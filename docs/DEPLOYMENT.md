# Развёртывание на VPS

Состав: Next.js приложение и постоянный worker, база в облачном Supabase. Worker запускает транспортную очередь, публикацию Reels, сбор Instagram Insights, рекламные правила и старые automation в отдельных циклах; выполняет обслуживание Instagram-токенов/очередей и проверку рекламных credentials. Контракты модулей и карта кода — в [PROJECT_GUIDE.md](PROJECT_GUIDE.md). Для полной установки применяются все миграции, включая рекламные `20261006000002_meta_ads_read.sql`, `20261006000003_meta_ads_manage.sql` и `20261007000001_ads_resources_automation.sql`. Контракт публикаций — в [PUBLISHING_API.md](PUBLISHING_API.md), статистики — в [INSIGHTS_API.md](INSIGHTS_API.md), фоновых рекламных правил — в [ADS_AUTOMATION_API.md](ADS_AUTOMATION_API.md).

## Подготовка базы

Для нового проекта примените все файлы `supabase/migrations` в порядке имён. API-ключи используются приложением; для миграций нужна PostgreSQL URI из Supabase **Connect → Session pooler** с заполненным паролем базы. В `.env.local` добавьте `DATABASE_URL=postgresql://...`; специальные символы пароля кодируются для URI.

```sh
npm ci
npm run migrate
```

Runner использует TLS с проверкой сертификата (публичный Supabase CA в `supabase/certs/prod-ca-2021.crt`; другой CA можно задать через `DATABASE_SSL_CA`), записывает применённые версии и их контрольные суммы в `open_autodm_migrations`. Повторный запуск пропускает применённые файлы. Для проекта, в котором исходные миграции ранее применили вручную, примените только новую транспортную миграцию через SQL Editor; runner рассчитан на начальную установку с ведением своей таблицы версий.

## Настройки и контейнеры

Заполните `.env.local` по `.env.example`. В `APP_OWNER_EMAILS` укажите email владельца панели: API и защищённые страницы принимают сессии только этих пользователей. Современные переменные: `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`. Старые названия также принимаются приложением. Docker-конфигурация использует современные имена.

`TOKEN_ENCRYPTION_KEY` и `CRON_SECRET` генерируются один раз. Сохраните исходный ключ шифрования вместе с резервной копией конфигурации: он нужен для чтения Meta-токенов и секретов интеграций после переноса. `.env.local` исключён из Git и Docker build context. `DATABASE_URL` требуется только машине, применяющей миграции; исключите его из окружения приложения и worker на VPS.

Укажите итоговый HTTPS адрес в `NEXT_PUBLIC_APP_URL` **до сборки**. Публичный Supabase URL и publishable key встраиваются в браузерную сборку. Секретный Supabase key передаётся контейнерам при запуске.

```sh
docker compose --env-file .env.local build app
docker compose --env-file .env.local up -d
```

Контейнеры получают суммарный лимит памяти 1152 MiB (app 768, worker 384) и по одному CPU. Это ограничение, фактическая загрузка проверяется после запуска. Приложение слушает только `127.0.0.1:3018`; поставьте существующий HTTPS reverse proxy перед этим портом. Существующий стек сервера можно подключить к контейнеру по общей Docker-сети вместо loopback-порта; не меняйте соседние сервисы.

Для существующего Caddy на niar42 используйте production override. Он подключает HTTP-приложение к `niar42-edge` под именем `open-autodm-app`; worker использует собственную сеть стека. Для другой сети задайте `CADDY_NETWORK`.

```sh
docker compose --env-file .env.local -f compose.yaml -f compose.production.yaml up -d --wait
```

Блок Caddy:

```caddyfile
autodm.niar42.com {
    import common
    reverse_proxy open-autodm-app:3000
}
```

Перед применением сохраните конфигурацию и проверьте кандидата через `caddy validate` внутри Caddy-контейнера. На niar42 Caddy 2.11.4 запущен с файлом конфигурации и `admin off`; конфигурация перечитывается через `docker kill --signal=SIGUSR1 niar42-caddy`. [Условия перезагрузки сигналом](https://caddyserver.com/docs/command-line#signals). Файл конфигурации смонтирован отдельно: изменяйте его содержимое с сохранением inode.

`GET /api/health` возвращает 200 при доступности базы и таблиц транспорта, публикаций и Instagram Insights. Рекламные таблицы и доступ Meta проверяются рекламными API отдельно. Состояние очереди и запущенного worker проверяется отдельно: задания должны переходить в ожидаемые состояния согласно контракту модуля. Контейнерные логи ограничены 3 файлами по 10 MiB на сервис.

Для управления через ИИ-агентов можно включить постоянный ключ владельца: `OWNER_API_TOKEN_HASH` (SHA-256 полного ключа `adm_…`) и `OWNER_API_USER_ID` (UUID существующего пользователя Supabase Auth). Ключ передаётся как Bearer; сервер проверяет текущего пользователя и `APP_OWNER_EMAILS`. Изменение runtime env требует пересоздания контейнеров. См. [управление без панели](AGENT_API.md).

## Порядок подключения Instagram

1. Откройте приложение и авторизуйтесь через Supabase.
2. Завершите существующий Meta setup wizard и зарегистрируйте HTTPS callback/webhook адреса.
3. Подключите Professional Instagram аккаунт через существующий OAuth.
4. Зарегистрируйте интеграцию и привяжите её к внутреннему account UUID через API.
5. Проверьте реальное входящее DM и состояние ответного сообщения, затем подключайте остальные аккаунты.

Права и режим Meta app проверяются при живом подключении. Успешные локальные тесты не подтверждают выдачу Meta permissions или доставку живых DM.

## Проверки перед выпуском

`npm test`, `npm run test:integration`, `npm run typecheck`, `npm run build`, `npm audit`. Docker image следует собирать под архитектуру VPS; локальная сборка Next.js отдельно проверяет код, а запуск контейнеров подтверждается на Docker-хосте.

При Supabase Free учитывайте рост базы от сообщений и debug logs. В этой версии транспорт чистит завершённые raw webhooks через 7 дней, сообщения и idempotency records через 30 дней. Нужны регулярный бэкап базы, сохранение ключа шифрования, наблюдение за незавершённой очередью и состояниями `delivery_unknown`. Пауза проекта Supabase делает health недоступным, pending задания остаются в базе.

## Проверка действующей установки

Адрес установки и расположение доступа указаны в локальном `.local/AGENT_ACCESS.md`. Перед зависимым действием проверь health, состояние контейнеров, нужные API и доступ Meta. Исходники на сервере и локальная ветка могут различаться; сопоставь их перед выпуском. История ниже фиксирует первоначальный запуск.

На niar42 файл `/opt/open-autodm/.release.json` хранит runtime commit, image, время выпуска, миграцию и подтверждения проверок. Сверяйте его с фактическими image обоих контейнеров. Документация может обновляться отдельным commit после сборки; её версия указана отдельно. Сохраняйте этот файл при синхронизации следующего выпуска. `.local/` исключён из Docker build context.

## Рекламные материалы и шаблоны

Расширение использует миграцию `20261011000001_ads_creative_assets.sql`. Примените её перед обновлением app и worker. Она добавляет частные staging-таблицы изображений и неизменяемые версии ручных шаблонов; новых переменных окружения нет. Cron maintenance удаляет истёкшие staging-записи. Локальные картинки передаются multipart, поэтому reverse proxy должен пропускать тело до 8 MiB + 64 KiB. Контейнерный Next.js endpoint работает в Node runtime.

Существующие операции имеют старый snapshot: расширение его состава может отменить такой plan при execute. Дождитесь завершения executing/uncertain операций по их контракту; остальные ещё не исполненные планы проверьте и подготовьте заново после выпуска. Новый plan hash нельзя подставлять в старую операцию. Сервисный шаблон не изменяет существующие ads автоматически.
